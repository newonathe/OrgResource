# 3. Project identity and fixed direction

The project has already been selected.

**Do not reopen the comparison between ProjectClose, ProjectStock, and OrgStock.**

The selected project is ProjectStock, refined and named:

**OrgResource: Student Organization Resource Planning and Allocation System**

The product's purpose is to help student organizations plan projects using resources they already own or are authorized to manage, coordinate resource requirements across departments, identify allocation conflicts, and determine genuine shortages before purchasing or sourcing additional materials.

Its primary focus is not simple inventory recording.

Its defining capability is:

**Connecting project-level resource requirements with actual inventory, existing commitments, resource availability, and allocation decisions across departments.**

The system should help an organization answer:

- What resources do we own or control?
- What resources are usable?
- Where are they stored?
- Which department is responsible for them?
- What does each upcoming project require?
- When does each project need those resources?
- How much stock is already committed?
- Are two projects competing for the same resources?
- Can resources be shared or reallocated?
- What is the actual shortage after accounting for available inventory?
- Which resources need to be purchased or sourced?
- Who currently has custody of a reusable item?
- Was the resource returned?
- Was it damaged, lost, consumed, or adjusted?
- What resources are frequently used?
- What resources are underutilized?
- What recurring demand patterns should influence future planning?

The system should be useful for a multi-department student organization.

The initial implementation should be scoped to ONE organization with multiple departments, not a university-wide platform.

It should be configurable enough to support different organization structures and resource categories without introducing unnecessary multi-tenant complexity.

# 4. Background and problem rationale

The project is motivated by publicly reported organizational resource-coordination issues at Ateneo.

A particularly relevant public case was reported by The GUIDON in its May 2025 article, *Following the funds: The gaps in the Sanggunian's financial processes*.

The report described interdepartmental coordination problems, including different departments requesting similar materials separately rather than coordinating and sharing resources.

This provides a documented example of a resource-coordination problem.

However, do not overstate the evidence.

The public report does not establish:
- The exact materials involved.
- Whether they were reusable.
- Whether they were already owned.
- Whether they were available at the same time.
- The exact financial loss.
- The frequency of the problem.
- Whether all Ateneo organizations experience it.

Another relevant example is MEA's public description of its MEA Room as an inventory hub with digital tracking and physical audits.

This is important counterevidence: basic inventory tracking is not sufficiently differentiated.

The application must therefore be designed around project-based resource planning, demand consolidation, date-aware availability, allocation management, and shortage analysis.

The project must not replace:

- OSA official project proposal submissions.

- SAPS.
- Official OSA document tracking.
- CFMO facility reservations.

The application should manage only resources that the student organization owns or is explicitly authorized to control.

# 6. Critical business rules and calculations

This section is central to the project.

Do not simply describe the application conceptually. Define the actual rules the software must enforce.

## 6.1 Date-aware availability for reusable resources

The application must account for overlapping reservations.

A simple total-stock calculation is insufficient.

For a reusable resource, define availability at time t as:

A(t) = U - SUM(Qi for approved or issued allocations overlapping t)

Where:
- A(t) = quantity available at time t.
- U = usable physical stock.
- Qi = quantity committed by an allocation.
- Only allocations whose date ranges overlap the evaluated time are counted.

Define date-range overlap precisely.

For two intervals [startA, endA] and [startB, endB], define whether they overlap, including whether boundaries are inclusive or exclusive.

Choose one consistent interval convention and apply it throughout the database, API, and service logic.

Explain:
- What happens when a project is rescheduled.
- What happens when an allocation is cancelled.
- What happens when an item is damaged.
- What happens when an item is returned late.
- What happens when an allocation is partially issued.
- What happens when a resource's usable quantity decreases.
- What happens when a new project requests already committed resources.

The system must prevent over-allocation.

## 6.2 Consumable inventory

For consumables, define:

Remaining stock = Opening stock + Receipts - Consumption +/- Adjustments

Also account for approved reservations that have not yet been consumed.

Define how the system prevents two projects from reserving the same consumable quantity.

Explain the distinction between:
- Physical on-hand quantity.
- Reserved quantity.
- Available-to-promise quantity.
- Consumed quantity.
- Damaged or lost quantity.

Do not subtract the same quantity twice.

## 6.3 Shortage calculation

Define how the system calculates actual unmet demand.

At minimum, distinguish:
- Total project demand.
- Existing usable inventory.
- Existing allocations.
- Available stock for the required period.
- Approved allocations.
- Remaining unfulfilled requirements.
- Additional quantity that must be sourced.

A shortage must not be calculated using a naive formula that ignores scheduling or allocation overlap.

Explain how reusable and consumable shortages differ.

## 6.4 Allocation approval

Define:
- Who can submit an allocation request.
- Who can approve it.
- Whether the resource custodian must approve.
- Whether administrators can override a conflict.
- Whether an override requires a reason.
- Whether rejected and cancelled allocations remain in history.
- Whether an approved allocation can be edited.
- How rescheduling is handled.

Do not assume every department can approve its own requests.

## 6.5 Resource custody

For reusable resources, track:
- Current custodian or responsible department.
- Current location, if relevant.
- Current condition.
- Whether the item is issued.
- Expected return date.
- Actual return date.
- Inspection result.

Distinguish physical inventory from custody.

An item that has been issued is still owned by the organization, but it is not available for another allocation.

## 6.6 Inventory integrity

Define the source of truth for inventory.

Avoid inconsistent designs where both a transaction ledger and freely editable quantity fields can disagree.

If maintaining a current quantity as a performance optimization, explain how it is updated atomically and reconciled against transactions.

Define how inventory adjustments are authorized and audited.
