## 2. New official-source discovery: maintained Java EE 8 features remain available on modern Java
**VERIFIED EXTERNAL FACT:** [Open Liberty Java EE platform 8](https://www.openliberty.io/docs/26.0.0.6/reference/platform/JavaEE.html) explicitly includes `beanValidation-2.0`; [Bean Validation 2.0 feature](https://openliberty.io/docs/26.0.0.4/reference/feature/beanValidation-2.0.html) lists actual `javax.validation.*` packages and supported JavaSE 8/11/17/**21**/25/26. [JAX-RS 2.1 feature](https://openliberty.io/docs/latest/reference/feature/jaxrs-2.1.html) lists JavaSE 21. These facts disprove any categorical claim that **Java 21 itself cannot execute `javax.validation`**. They do **not** prove a current Spring Boot4/Jersey4 app can use the Liberty's JavaEE8 built-in provider.
**Critical separation:** [Liberty Spring Boot2 feature](https://openliberty.io/docs/26.0.0.9/reference/feature/springBoot-2.0.html) and [Boot4 feature](https://www.openliberty.io/docs/26.0.0.6/reference/feature/springBoot-4.0.html) both exist. Yet Liberty's Spring Boot documentation explicitly says **Boot-app features do not integrate automatically with Liberty Application Security/JAX-RS and similar container features**; it expects Spring Boot starters for those functions. [Liberty 4 guide](https://github.com/OpenLiberty/ci.maven/blob/main/docs/spring-boot-support.md) specifies the `springBoot-4.0` feature and Jakarta EE 11 compatible Servlet6.1, not a JavaEE8/native-javax Boot4 integration. Liberty JAX-RS implementation need not equal the **Jersey** required by the course, and support for a server does not repair unmaintained Spring5/Boot2 bundled libraries. **Candidate LL1 = investigate, not approve.** A dual deployment/container feature list is not evidence that both namespaces and the required Spring/Jersey integration coexist safely in one app.

## 4. Identity research: why email-free invitation and account recovery require design
**VERIFIED EXTERNAL SECURITY GUIDANCE:** [NIST SP800-63B-4 July2025](https://pages.nist.gov/800-63-4/sp800-63b.html) describes password-only login minimum **15** chars, no forced composition/periodic rotations, blocklist screening; saved recovery codes are an officially described recovery method with **at least 64 bits** random entropy. These are **external risk-based benchmarks for our design**, not an invented Ateneo requirement or NIST certification claim. [OWASP password reset](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) requires secure, single-use, non-enumerating recovery; offline methods are possible. [OWASP security questions](https://cheatsheetseries.owasp.org/cheatsheets/Choosing_and_Using_Security_Questions_Cheat_Sheet.html) does NOT endorse knowledge-based questions as sole authentication. [Spring Security password storage](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html) recommends adaptive hashes and per-host tuning; [OWASP session cookies](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) recommends Secure/HttpOnly/SameSite and host-only cookies; [OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) deny-by-default and current permission check every request.

### Proposed exact synthetic-auth contract (DESIGN RECOMMENDATION, NOT IMPLEMENTED)
1. **Bootstrap**: named authorized operator (user) provisions a *single-use*, bounded first-OWNER claim through an **offline CLI or equivalent non-public secure channel**, requiring running original environment checks. Claim yields a private, conspicuously **UNVERIFIED/FICTIONAL** organization, never automatically an officially recognized Ateneo unit. No anonymous public `POST /orgs` may create verified org affiliation. Two concurrent claims yield **exactly one winner**; bootstrap permanently disabled afterward unless explicit audited recovery.
2. **Account identifier and password**: opaque internal user UUID/username key unique under defined normalization; password-only path requires >=15-character password, supports passphrases, blocklist and generic login failure, no artificial composition/automatic expiration; adaptive bcrypt/PBKDF2/Argon2 appropriately tuned on real host, password never logged; optional `verified_email` remains NULL/false when not actually verified. NIST principles are best-practice design targets.
3. **Recovery**: issue multiple one-time unpredictable saved recovery codes (**recommend >=128-bit each**, above NIST 64-bit minimum) at setup, store only slow/keyed hashes/identifiers, display once; code use rotates password, invalidates active sessions and prior codes as policy dictates, raises audit event, requires throttling. No 'forgot password' email if no provider exists; if owner loses password and all recovery material, **account recovery BLOCKED** without an independently authorized human process. Do NOT claim real identity proof from help desk or security questions.
4. **Invitations**: OWNER/ADMIN invites allowed role <= their grant authority (not OWNER by ADMIN), 128+bit random bearer token displayed once via confidential manually delivered channel for fictional testers, hashed in DB, expires <=7d (proposed), atomic single use; redeem requires signed-in user. Since the channel does not confirm intended student email, **token possession alone is only a prototype authorization signal**, not verified real-world identity. No phone, Twilio or paid email required; no real user onboarding allowed until delivery/risk verified.
5. **Membership**: role {OWNER,ADMIN,CUSTODIAN,LEAD,MEMBER} and status {ACTIVE,SUSPENDED,LEFT}; every API checks current active membership scoped to org (not a stale session role). OPERATOR infrastructure-only, no implicit access to tenant content. Last ACTIVE OWNER cannot leave/demote, ADMIN cannot grant OWNER. Ownership transfer must record old owner→target ACTIVE ADMIN, acceptance in bounded time, current user+org auth on both steps, explicit prevention of simultaneous last-owner removal. No unilateral `@ateneo.edu` ownership grants.
6. **Sessions and CSRF**: HTTPS same-origin, `__Host-`-prefixed Secure HttpOnly SameSite cookie, no JS/localStorage token; CSRF header on state-changing browser POST, rotate session ID on login/password change, revoke after logout/suspension/recovery, absolute and idle TTLs (proposal <=7d and <=12h, not yet benchmarked), server-side recheck membership. External TLS/cookie support must actually work on selected IP/hostname.
7. **Boundary**: all publicly readable demo information is fictional; authenticated write operations available only to invited fictional test users. Real org administrator assertion, real student identity and adoption require separate documented approval and privacy handling; don't invent institutional signup.

## 5. Data-model gap: existing eleven-table V2 draft cannot implement local recovery as described
Current [10](10_EERD_AND_DATA_DICTIONARY.md) `user_account` has `auth_provider`/`auth_subject`, but **no password credential table or verified reset method**; `invitation` has one-use tokens but not an identity verification channel; `membership` + `organization` lack a durable ownership transfer request. If local auth chosen, **the provisional eleven-entity count is an estimate, not a usable final migration**. Need at minimum proposed `local_credential(user_id UQ,username_key UQ,password_hash,hash_scheme,credential_version,changed_at,disabled_at?)`, `account_recovery_code(id,user_id,code_hash UQ,used_at?,created_at,revoked_at?)`, `ownership_transfer(id,org_id,from_membership_id,to_membership_id,token_hash?,expires_at,status,accepted_at?,created_at)` plus a deliberate session storage design (DB table or safe restart-invalidating in-memory session, tested). Exact class/column definitions, FK/non-null/cascade, role transitions and recovery rules must be finalized and independently reviewed **before code**. This does **not silently create a table for the course five-entity app**; these are future V2-only proposals.
