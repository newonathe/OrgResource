## 3. Two critical business-rule differences
**Stock availability:** Academic V1 reusable `available=T - APPROVED - ISSUED` regardless of project date. Consumable `available=remaining T - APPROVED`; whole batch RETURN restores reusable availability and CONSUME permanently subtracts from stock. V2 draft uses half-open time-window approved holds, `outstandingIssued`, and later-start bookings. These are **different allocation algorithms**; allowing both without a named API/version and clear UI explanation could permit a user to believe a future reservation exists in the original system when it cannot.
**Entity and ownership semantics:** Academic `Department` is an internal organization team owning a `Project`. Proposed V2 `Organization` is a cross-tenant workspace; it is NOT equivalent to Department and cannot replace it without a documented model translation. V2 `project.lead_membership_id` is not equivalent to `Project.departmentId`. For true compatibility, either retain a Department object within tenant schema and all five original entity behaviors, or preserve and demonstrate isolated original source and obtain **explicit approval** for differences in supported public service. User has NOT approved changing legacy contract.
**Response/idempotency differences:** Academic IDs are numeric Long; V2 UUID public IDs. Academic create 201 and other successes 200; V2 introduces 202/422/412/429/503, conditional versions, body idempotency keys and principal-specific filtering. These may be security improvements, but not byte-compatible responses. The same paths cannot be exposed in public without authentication: security overrides public unauthenticated equivalence and must be a documented compatibility exception.

## 4. Independent modern-runtime compatibility updates
**New fact C-01:** [Spring Boot system requirements](https://docs.spring.io/spring-boot/system-requirements.html) says Boot4.1.2 requires Java17+, Spring Framework7.0.10+. [Official managed dependency list](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html) currently records Jersey4.0.3, `jersey-media-json-gson`, `jersey-media-json-jackson3` and `spring-boot-starter-gson`. [Jersey 4.0.3 release](https://github.com/eclipse-ee4j/jersey/releases) explicitly added Jackson3 support in Oct2026. [Spring JSON guide](https://docs.spring.io/spring-boot/reference/features/json.html) says Jackson2 bridge is **deprecated and slated for removal in 4.x**. Thus prior statement 'Boot4 + Jersey requires Jackson2 bridge' is **outdated for Jersey4.0.3** and must not be used as a mandatory long-lived dependency. Alternative Gson/Jackson3 providers exist as artifacts; actual selected provider, no duplicate auto-registration and JSON behavior **NOT TESTED**.
**New fact C-02:** [Hibernate Validator current release index](https://hibernate.org/validator/releases/) lists **6.2.6.Final, 2026-10-13** as latest javax-series service update (older 6.2 page still displays 6.2.5 Maven example). Series status remains **limited-support**, Java 8/11/17; it is not a supported Jakarta3/Boot4 validator. [Validation 3.1 specification](https://jakarta.ee/specifications/bean-validation/3.1/jakarta-validation-spec-3.1.html) explicitly changed annotation package `javax.validation.*`→`jakarta.validation.*`. [Spring Framework current validator integration](https://docs.spring.io/spring-framework/reference/core/validation/beanvalidation.html) expects `jakarta.validation.Validator`. **Still no verified single-process supported public Boot4 service exercising full native javax Bean Validation with Jersey/JPA.**
**Technically plausible but UNPROVEN route:** an isolated actual Java17 `javax.validation` provider module could be researched, with clear classloader/bean-validation provider boundary and no duplicate Hibernate Validator dependencies. It may fail support/security/complexity and no-spend constraints; NEVER infer success by Maven coexistence, or authorize Codex based on this suggestion. A separate actively runnable academic Java8 module plus supported product would still need owner acceptance of the namespace boundary.
