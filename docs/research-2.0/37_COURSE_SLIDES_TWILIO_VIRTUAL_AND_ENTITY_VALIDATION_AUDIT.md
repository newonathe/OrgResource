## 2. MC-26 — two separately required validation execution paths
**Course source and O14**: `Misc JPA --Validation` p5 and timestamped V03 [0534–0566] describe validation at ORM `save()`. O14 real JPA entities contain `javax.validation` constraints, not only request DTOs.
**VERIFIED EXTERNAL FACT:** [Jakarta Persistence 3.2 `3.7 Bean Validation](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html) delegates automatic validation on pre-persist/pre-update/pre-remove lifecycle to the associated **Jakarta Bean Validation** provider. [Jakarta Persistence ValidationMode](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/ValidationMode.html) specifies AUTO/CALLBACK/NONE; [current Jakarta EE tutorial](https://jakarta.ee/learn/docs/jakartaee-tutorial/current/persist/persistence-intro/persistence-intro.html) confirms entity constraints on persistence events. Modern Spring/Jersey4 native provider uses **`jakarta.validation`**, whereas O14 source uses **`javax.validation`**.
**MATERIAL COMPATIBILITY GAP:** proving explicit old `javax.validation.Validator.validate(dto)` on a request **does not prove** a modern Jakarta ORM will automatically reject old Javax entity annotations at persistence time. This is a reason to demand either a demonstrably active compatibility adapter/transactional validation boundary covering **every entity write**, or a separately explicitly approved active original runtime behavior, with real tests. A one-off POST negative test that only invokes request DTO validation is **insufficient** to mark fully preserved course Javax behavior.
**Future acceptance VA-13..VA-15 (NOT RUN):**
- **VA-13:** For original-equivalent entities with invalid `javax @NotNull`/`@Min`, invoke direct JPA repository `saveAndFlush` or entity-manager persistence **without going through the DTO request validator**. Verify a constraint failure, rollback and zero new rows. Test UPDATE and create, including cascades/batch operations and scheduler writes. Compare original O14 Javax ORM behavior and candidate public app at fixed SHA.
- **VA-14:** Verify which exact Javax vs Jakarta constraint provider executes persistence lifecycle, or ensure explicit centrally enforced Javax validation before every persistence mutation. Demonstrate no silent bypass on service/background jobs/bulk updates; DB NOT NULL/CHECK is a defense-in-depth constraint but **does not replace** literal Javax execution for course compliance.
- **VA-15:** Verify both error paths: HTTP bad DTO returns sanitized 400 without stack traces; programmatic/ORM invalid entity reaches the transaction boundary safely (no partial data), maps to documented error, and does not return a misleading 404. Run on actual MySQL and chosen modern Jersey/Spring stack.
These extend CP8/CP9 provider checks; **none executed**.
