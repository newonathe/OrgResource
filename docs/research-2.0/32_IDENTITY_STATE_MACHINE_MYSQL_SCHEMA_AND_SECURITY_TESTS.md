## B. Verified external technical corrections
**E-CP5-01 — MySQL temporal trap:** [MySQL 8.4 Date/Time](https://dev.mysql.com/doc/refman/8.4/en/datetime.html) explicitly limits `TIMESTAMP` to 2038-01-19 03:14:07 UTC and converts between session time zone and UTC. `DATETIME(6)` has wide range, does not automatically time-zone-convert. **Design recommendation:** use `DATETIME(6)` for V2 business instants and created/updated/event times, stored by application as **UTC without offset**, with API RFC3339 `Z` and UI Asia/Manila, explicit clock and JDBC/connection UTC rules. Do NOT silently migrate academic V1 `LocalDateTime` Philippine local timestamps. Test time-zone round trip, year 2040, boundary end/start and server zone changes.
**E-CP5-02 — FK NULL semantics:** [MySQL 8.4 CREATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/create-table.html) says InnoDB composite foreign keys have MATCH SIMPLE semantics: any partially NULL composite key can bypass lookup. Parent must be unique and non-null by our design; mandatory child `org_id` and `parent_id` NOT NULL, named composite FK to parent (`org_id,id`). Use restrictive delete and actual negative SQL tests. A simple FK to parent numeric id is **not** tenant-safe when org_id can mismatch.
**E-CP5-03 — MySQL CHECK limitation:** [MySQL 8.4 CHECK](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html) rejects expressions referring to other tables and subqueries. Therefore `COUNT(active OWNER)>=1` across memberships **cannot be guaranteed by a normal CHECK constraint**. Serialize ALL role/leave/suspend/transfer/owner operations by locking the same organization row, and keep at least one ACTIVE OWNER at commit; prove concurrency with two simultaneous demotions and account suspension.
**E-CP5-04 — Session table accounting:** [Spring Session JDBC](https://docs.spring.io/spring-session/reference/configuration/jdbc.html) uses **two** physical tables by default, `SPRING_SESSION` and `SPRING_SESSION_ATTRIBUTES`, with vendor-specific schema scripts. Do not claim “11+one session table.” Use the exact vendor MySQL schema from selected current Spring Session version and explicit DB migration; do not handwrite an incompatible substitute. A restarted API session and revocation must be tested.
**E-CP5-05 — Session and CSRF:** [Spring Security session fixation](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html) rotates session ID on login. [Spring Security CSRF SPA](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html) requires token refresh after authentication/logout, and CSRF even for login and logout. Cookies authenticate in the **Cookie** request header, not Authorization. Secure/HttpOnly/SameSite cookies + anti-CSRF header on mutations; positive/negative authentic REST tests are mandatory.
**E-CP5-06 — Password/recovery:** [NIST SP800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) requires at least 15-character passwords for single-factor use, no arbitrary composition rules, salted adaptive hashing and 64+ bits for saved recovery codes; recommends invalidation of used saved code and issuance of replacement. [Spring Security password storage](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html) supports delegating encoder + transparent scheme version. We **recommend >=128 random bits** per saved recovery code; this is our higher design bar, not a course/institutional rule. Real CPU tuning must be tested on free host.
**E-CP5-07 — Reservation isolation:** [InnoDB isolation](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) warns mixing normal snapshot reads with locking reads at REPEATABLE READ; READ COMMITTED creates fresh read views but needs **all** resource writers to lock same resource first, otherwise phantoms still risk overbooking. This identity research does NOT claim inventory race tests passed.

## C. Identity vs membership vs official institution authorization
**DESIGN RECOMMENDATION:** for synthetic technical demo, usernames/passwords prove only account authentication. Invitation possession and active membership can authorize one **fictional private workspace**, but do not verify student identity, government ID, an official Ateneo org, an @ateneo.edu administrator, or campus authority. Public landing page may show fictional demo info; public anonymous mutations, first-visitor OWNER and unverified official affiliation are denied. Any real student/stakeholder onboarding, data controller selection, user interviews, institutional integration or pilot is separately authorized future work. User's existing hard course requirements remain separate.

### C1. Exact provisional roles
- `OWNER`: workspace governance, appoint ADMIN, initiate OWNER transfer, ordinary member admin (subject to last-owner rule). **Cannot silently waive second-party consent for ownership transfer.**
- `ADMIN`: manage roles below ADMIN (MEMBER, LEAD, CUSTODIAN), invite/suspend eligible roles, no self-OWNER, no OWNER grant/demotion/transfer completion.
- `CUSTODIAN`: resource/stock/approval/issue/return/consume according to authorized tenant; cannot manage identity.
- `LEAD`: project/requirement/allocation requests on owned/assigned projects; cannot approve own custody without CUSTODIAN grant.
- `MEMBER`: eligible tenant catalogue and own redacted custody; no stock/role mutations.
- `OPERATOR`: database/process/backup service access **not** an organization role; has no tenant-data API access by default. A break-glass operator-content role is NOT specified/approved.

All privileged mutations must check `user_account.status=ACTIVE`, `membership.status=ACTIVE`, `organization.status=ACTIVE` and the current role **at request time/inside the write transaction**. Never trust role from a stale browser session. User can belong to two fictional orgs with independent roles; selecting an org is not proof of membership.

### C2. State machines (DESIGN RECOMMENDATION, not code)
| Object | Allowed event / preconditions | New state or effect | Denials |
|---|---|---|---|
| Account `ACTIVE` | authorized self-change password, valid saved recovery, operator-controlled disable | `ACTIVE` with incremented credential_version, all prior sessions invalid; or `DISABLED` | login as disabled; recover with used code; unknown operator override |
| Account `DISABLED` | operator-reviewed controlled re-enable only, real identity process not defined | `ACTIVE` only after policy acceptance | automatic self-reactivation |
| Membership `ACTIVE` | OWNER/ADMIN policy suspend, authorized user leave, valid OWNER transfer | `SUSPENDED` or `LEFT`, authorization immediately revoked; `OWNER` role changes serialized | last ACTIVE OWNER removal, ADMIN self-escalation |
| Membership `SUSPENDED` | authorized OWNER/ADMIN reinstatement | `ACTIVE` with current rights | self-unsuspend, unverified actor |
| Membership `LEFT` | new valid invite redeems against same (`org_id,user_id`) unique row | `ACTIVE` as fresh authorized membership with audit (provisional) | silent automatic rejoin |
| Invitation `INVITED` | signed-in eligible fictional account redeems exact unused token while current time < expiresAt | `ACCEPTED`, linked membership created/reactivated atomically | double redeem, revoked/expired, cross-org, unauthorized target |
| Invitation `INVITED` | authorized inviter/owner revokes; scheduled timeout | `REVOKED` or `EXPIRED` | accepted invite reversed after consumption |
| Ownership transfer `PENDING` | same org, initiator ACTIVE OWNER, intended recipient ACTIVE ADMIN, unexpired, recipient authenticated+accepts | `ACCEPTED`; target becomes OWNER, old OWNER becomes ADMIN **atomically** under org lock (provisional policy) | old/target disabled/LEFT, wrong account, race, stale request, expiry |
| Ownership transfer `PENDING` | current initiating OWNER revokes, time expires | `REVOKED` or `EXPIRED` | final states reopened |
| Session `ACTIVE` | logout, password reset, account disabled, idle/absolute expiry, membership denied | `REVOKED`/expired and no authorized content | old session still works after reset |
| Saved recovery code `UNUSED` | valid account+code, strong password reset, rate limit under account lock | `USED`; credential version increments, new recovery material issued once | concurrent reuse, replay after restart, stale session |

**Policy question still OPEN:** Should ownership transfer demote old OWNER to ADMIN automatically, or promote target while old retains OWNER until explicit subsequent step? Table above proposes atomic transfer, **not a user decision**. This is a material API/scope choice. Neither option permits a moment with zero active owners.

### C3. Lock and transaction ordering — proposed
1. **First workspace bootstrap** is an **offline/operator-only** operation, never public “first visitor becomes OWNER”. Atomic organization + user credential + membership `OWNER`, with a DB unique bootstrap guard or operator controlled one-time setup mark; only fictional org labels. First/second simultaneous bootstraps yield exactly one accepted initial claim. Multiple **test** orgs may be separately seeded by authorized operator.
2. **Invite create/revoke/redeem:** authenticate actor, use `organization.id FOR UPDATE` to serialize member-grant policy and tenant state; lock invitation id for single consumption; conditional UPDATE where status INVITED and current time < expires; insert or re-enable unique (`org_id,user_id`) membership; audit and commit. Unused token never logged; raw token returned once to an authorized inviter only in a no-store response; delivery is confidential manual for fiction, **not identity attestation**.
3. **Member role, suspend, leave, transfer:** lock organization first; membership rows in ID ascending order, then pending transfer row(s), re-check actor and target at write-time; enforce current ACTIVE OWNER count and permission matrix; transition membership(s), invalidate affected rights, audit in same transaction. On transfer accept, target=OWNER and initiator=ADMIN in one commit and state=ACCEPTED. Never call provider network under lock. Use CHECK constraints for single-row legal status/role, not cross-row owner count.
4. **Password recovery:** serialize on account row, atomic unused recovery-code claim, change password_hash and credential_version, write redacted audit, and revoke session epochs. DB-level unique code and atomic one-use mark. Return no raw saved secrets in log; issue replacement code once via secured authenticated screen. If all recovery material lost, real-identity recovery remains **BLOCKED** (no email/SMS/provider available).
5. **Disabled-member immediate denial:** verify account and membership with fresh DB state for each relevant access, including GET, activity, export, operation receipt, and downloads. An account-wide password reset invalidates all sessions, a membership suspension denies the org immediately but may retain same user's membership in unrelated org. Test multi-tab and concurrent requests.
6. **Deadlock or stale version:** roll back, bounded explicit retry only if operation idempotency durable; after retry exhaustion return sanitized 409/503 as specified. No success before DB commit.

## D. Revised physical MySQL logical schema (V2 ONLY; no DDL executed)
Starting *provisional* 11 original V2 tables in [10](10_EERD_AND_DATA_DICTIONARY.md) and [31](31_JAVAX_RUNTIME_AND_EMAIL_FREE_IDENTITY_RESEARCH.md):
| Entity/table | Required field-level precision / constraints | Why needed |
|---|---|---|
| Existing `organization` | `id BIGINT PK`, `public_id`, `slug UNIQUE`, `display_name`, `status ACTIVE/CLOSING/CLOSED`, `version`, `created_at DATETIME(6) UTC`; P0 **omit** official affiliation or leave unverified NULL | Tenant root and serialization lock; do not assert campus approval |
| Existing `user_account` | `id PK`, `public_id`, `auth_provider=LOCAL`, `auth_subject VARCHAR(64)` with unique (`auth_provider,auth_subject`), `status ACTIVE/DISABLED`, `credential_version BIGINT >=0`, timestamps UTC. Username only in `auth_subject`; lowercase ASCII 3–64 recommended, not a second duplicate username column | Identity subject and global invalidation epoch; future provider extensions separate |
| Existing `membership` | `id PK`, `org_id NOT NULL`, `user_id NOT NULL`, `role`, `status`, `version`, `UNIQUE(org_id,user_id)`, `UNIQUE(org_id,id)`, FK org→org and user→account, created/updated UTC; no duplicate after leave | Durable tenant authorization and single role |
| Existing `invitation` | `id PK`, `org_id NOT NULL`, `token_hash BINARY(32) UNIQUE NOT NULL`, `role in ADMIN,CUSTODIAN,LEAD,MEMBER` (OWNER never by invite in P0), `status INVITED/ACCEPTED/EXPIRED/REVOKED`, `invited_by_membership_id NOT NULL`, `intended_user_id NULL`, `accepted_by_user_id NULL`, `expires_at DATETIME(6) UTC`, timestamps; composite FK `(org_id,invited_by_membership_id)` and extra bound account FKs. **Remove required invitee_email_hash** for synthetic bearer mode; do not store fake email | No external email service; invite possession ≠ verified identity. Optional intended_user_id can bind invited *known* fictional account |
| **NEW V2 `local_credential`** | `user_id BIGINT PK FK`, `password_hash VARCHAR(255) NOT NULL` with scheme identifier (or DelegatingPasswordEncoder prefix), `changed_at DATETIME(6)`; no duplicate username_key: local login name is existing account `auth_subject` | Actual local password verification, hash upgrade |
| **NEW V2 `account_recovery_code`** | `id BIGINT PK`, `user_id FK NOT NULL`, `code_hash BINARY(32) UNIQUE NOT NULL`, `created_at`, `used_at NULL`, `revoked_at NULL`, `batch_id UUID`. Unique hash over >=128-bit random code; no plaintext in DB | Saved offline password recovery and single-use |
| **NEW V2 `ownership_transfer`** | `id BIGINT PK`, `org_id NOT NULL`, `from_membership_id NOT NULL`, `to_membership_id NOT NULL`, `status PENDING/ACCEPTED/REVOKED/EXPIRED`, `version BIGINT`, `expires_at`, `created_at`, `accepted_at NULL`; both membership references via composite same-org FK; `CHECK(from<>to)`. At most one pending transfer per org via application org-lock and ideally tested generated-column unique index for PENDING slot | Verifiable two-party authority change, no externally emailed token needed |
| **EXTERNAL library-managed 2 tables** | `SPRING_SESSION`, `SPRING_SESSION_ATTRIBUTES` from version-matched **MySQL-specific** official Spring Session JDBC schema; principal ID, idle/expiry, index, session attribute storage, secure serializer; no hand-designed single table | Server-side persistent session and restart/revocation ability |

**Physical table accounting:** 11 original draft entities + 3 new justified application tables + 2 library session tables = **at least 16 physical tables** for this local-auth choice. This is NOT final: the older V2 draft omitted original **Department**; if public V2 must also preserve its own original Department entity/departmentId semantics, add ≥1 table and link project (≥17 total). Separate bootstrap/recovery operations could require further tables after security review. **Table count is derived design arithmetic, not a migration result or a course-required maximum.** The original academic application remains its own **five-entity** runnable artifact. Do not claim a 16-table public rewrite fully preserves the course without exact approved route/domain mapping [30](30_ORIGINAL_26_ROUTE_CROSSWALK_AND_RUNTIME_CORRECTIONS.md).

**Foreign keys / deletions:** tenant child with mandatory parent always `(org_id,parent_id) NOT NULL` plus indexed `UNIQUE(parent.org_id,parent.id)`; use `ON DELETE RESTRICT` for memberships/invitations/transfers/stock/audit (except audited retention purge workflow). Global user ID references are valid only when tenant membership explicitly checked. Sensitive recovery code/session records can be deliberately purged per retention, but never cascade delete stock/audit evidence. Test FK mismatches and no accidental identity deletion.
**Time:** all new V2 instants use `DATETIME(6)` with application UTC; input/output RFC3339 including offset; project original PHT `LocalDateTime` is preserved *only in original course executable*. Test 2040, timezone set +08 vs UTC, boundaries, expiry near midnight.
**Checks:** MySQL can enforce single-row `CHECK` for quantity/state and `CHECK(from<>to)`; it cannot check last owner across multiple rows. All owner-affecting APIs and worker changes MUST use organization lock. Session/credential/transfer schema must be a migration on a separate V2 database, not applied to academic MySQL in place.

## E. Provisional HTTP identity API deltas
| Intent | Proposed path/method | Guard and response | Required failures |
|---|---|---|---|
| CSRF/setup | `GET /api/v2/session` | Authenticated principal and memberships or 401; anonymous CSRF bootstrap separate controlled endpoint | no credential/session leak; CSRF token fresh on auth |
| Password login | `POST /api/v2/auth/login` | valid username/password → server session, rotate ID; 200 sanitized session | 401 generic, 429 throttled; CSRF verified |
| Logout | `POST /api/v2/auth/logout` | CSRF + current session → revoke/invalidate, 204 | old cookie cannot resume; replay harmless |
| Recovery | `POST /api/v2/auth/recover` | username+unused saved code+new password → account credential epoch increment and old session denial | generic invalid code, 429, reuse/conflict after success |
| Issue invite | `POST /api/v2/orgs/{orgId}/invitations` | OWNER/ADMIN allowed role; raw token **one-time** 201 no-store | 403 role escalation, 409 duplicate active policy, 404 org foreign, 429 |
| Redeem invite | `POST /api/v2/invitations/redeem` | auth+token → active tenant membership, 200 | reused/expired/revoked 409, intended user mismatch 403, foreign 404 |
| Role/suspend | `POST /api/v2/orgs/{orgId}/members/{id}/role` etc | check org lock, member/version, no last OWNER | 403 privilege, 409 LAST_OWNER, 412 stale |
| Ownership initiate/accept | `POST /api/v2/orgs/{orgId}/transfer-ownership` and `POST .../accept-transfer` | initiation current OWNER, acceptance exact target ADMIN, 200 on accepted | different account 403, stale/expired 409, concurrent 1 winner |
| Public org creation | `POST /api/v2/orgs` | **DISABLED in synthetic P0** pending user review; operator-only offline creation of labeled fictional tenants | 403/404 fail closed |

These are **recommended** route/response shapes, not executed Jersey code and not exact legacy `/api` mappings. Never replace 26 original academic GET/POST calls silently.
