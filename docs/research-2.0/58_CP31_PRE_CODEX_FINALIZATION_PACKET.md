## 4. Canonical state and arithmetic contract

Resource kind REUSABLE or CONSUMABLE. Whole-unit integer 0–1,000,000; operation quantity positive 1–1,000,000. Define T = physical available-plus-custody quantity for reusable and physical remaining total for consumable; H = effective APPROVED holds; I = outstanding ISSUED reusable custody. Compute with one injected clock sample per operation and checked integral arithmetic.

effectiveApproved(a, now) = (a.status == APPROVED && a.project.endAt > now).
H(r,now) = sum quantity of effectiveApproved allocations whose requirement refers to r.
I(r) = sum quantity where status == ISSUED and resource.kind == REUSABLE.
available(REUSABLE) = T − H − I.
available(CONSUMABLE) = T − H.
covered(requirement,now) = sum quantity of ISSUED, RETURNED, CONSUMED and effectiveApproved allocations for that requirement.
shortage = max(0, requirement.quantity − covered).
All derived quantities must be >=0 and within permitted bounds; contradictory persisted data returns a monitored integrity failure rather than clamping to plausible numbers.

**DESIGN RECOMMENDATION**: original global holds and whole-batch returns, not time-window optimization.

**SOURCE/CRITIQUE RECONCILIATION:** the original Project entity has startAt/endAt but no independent workflow status. CP29's public Project.status DRAFT/ACTIVE/CANCELLED/CLOSED is not paired with actual status-transition endpoints; do not invent a state machine. **Recommended P0 correction:** store startAt/endAt and compute read-only ProjectView.timePhase UPCOMING/IN_PROGRESS/ENDED from one injected clock; keep source-compatible create/update/delete, not an unimplemented ACTIVATE/CLOSE action. A future explicit cancellation workflow would require a separate approved amendment. Dates are exclusive-end for holding and issuing. PENDING has no hold. approve changes PENDING→APPROVED only when project active, requirement uncovered balance and available stock permit. APPROVED reusable issue changes H to I and appends ISSUE movement with deltaTotal=0, deltaIssued=+q. ISSUED reusable return changes I down by q with RETURN deltaTotal=0, deltaIssued=−q and status RETURNED; covered remains q. APPROVED consumable consume changes H down by q and T down by q with CONSUME deltaTotal=−q, deltaIssued=0 and status CONSUMED; covered remains q. APPROVED cancel releases H without physical movement and sets CANCELLED; PENDING cancel likewise. Historical approvedAt never reset. A never-approved PENDING/CANCELLED allocation may be physically deleted only if no dependent movement/mandated record. An ISSUED item is never automatically returned at project end.

At exact project.endAt, effective APPROVED hold and its requirement coverage cease immediately even if persisted row says APPROVED. Expose expiredPendingCleanup=true,isEffectiveHold=false until scheduler records CANCELLED with cancellationReason=EXPIRED. Scheduler must not create physical return/receipt movement. Status enum PENDING, APPROVED, ISSUED, RETURNED, CONSUMED, CANCELLED; there is NO standalone EXPIRED allocation status. Use resource/project/requirement/allocation consistent lock order and post-lock revalidation; no direct user-write to computed availability.

Ledger: immutable INITIAL, RECEIPT, ADJUST, ISSUE, RETURN, CONSUME movements, each with org/resource/operation linkage, deltas and checks. T equals sum of deltaTotal for that resource (subject to carefully specified import baseline); I equals sum of deltaIssued for reusable. Reject a negative T, H or I; audit reconcile source T against the ledger. Durable operationId uniqueness survives response loss, 48+ hour replay, restart and expiry of transient HTTP idempotency receipts. Nonzero initial stock generates INITIAL movement. **To preserve actual runtime Resource deletion:** a never-used zero-stock Resource may be created without a zero-value movement, then physically deleted when there are no Requirements, custody or history. For a previously moved Resource, prohibit destructive deletion and archive; if exact historical R04 after stock adjustment must delete, disclose the incompatibility and resolve course equivalence explicitly rather than claim full parity. This is a deliberate design trade-off requiring acceptance fixture.
