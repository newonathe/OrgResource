## 1. Primary-source correction to prior CP11: generic default vs actual MySQL.Free version are DIFFERENT
**E-CP12-01 — Oracle release timeline, dates distinguished:** [Sep29 default announcement](https://docs.oracle.com/en-us/iaas/releasenotes/mysql-database/heatwave-97x-default-track.htm) changed the **general new DB default** to MySQL **9.7.2 LTS**. [Oct20 release note](https://docs.oracle.com/en-us/iaas/releasenotes/mysql-database/heatwave-2610-974-8413.htm) supersedes that with **9.7.4 LTS** as the general default for new DB systems; MySQL **8.4.13 LTS** and **26.10.0 Innovation** are selectable on eligible **regular** systems. CP11 language treating September's **9.7.2** as the current general default is **OUTDATED**.
**E-CP12-02 — Always Free version selection differs:** [Always Free feature restrictions](https://docs.oracle.com/en-us/iaas/mysql-database/doc/features-mysql-heatwave-service.html), [Oracle Advanced Options](https://docs.oracle.com/en-us/iaas/mysql-database/doc/advanced-options.html) and [DB System Upgrade](https://docs.oracle.com/en-us/iaas/mysql-database/doc/mysql-server-upgrades.html) explicitly say **MySQL.Free cannot select a version; it is created with the *highest available version* and is upgraded to the highest available on each maintenance cycle**. Because Oct20 release lists **26.10 Innovation** as available alongside 9.7.4/8.4.13, Oracle's **general default 9.7.4 does not independently prove the actual MySQL.Free version/track**. The literal interpretation of "highest available" versus "default new DB" needs current account evidence; neither **9.7.4** nor **26.10** may be asserted as the actual free server without provisioning. User retains strict $0 ceiling, so do not create an account simply to answer this. **Material unresolved hosting version gate.**
**E-CP12-03 — self-managed 8.4 package choice:** [Oracle Linux9 ARM64 MySQL8.4 repository](https://yum.oracle.com/repo/OracleLinux/OL9/MySQL84/community/aarch64/index.html) contains MySQL8.4.13 for aarch64. [MySQL release model](https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html) permits selecting an **8.4 LTS repo track** rather than innovation. **DESIGN RECOMMENDATION (NOT APPROVED):** for a deadline-constrained small synthetic OrgResource P0, prefer *controlled MySQL8.4 LTS* on an eligible OCI A1 VM over an unpinnable managed DB until account-specific/MySQL.Free lifecycle and backup risks are proven. That recommendation is about **version/recovery predictability**, not proof of lower total labor or production fitness; managing Linux/MySQL backups/patches is nontrivial. The original academic JPA/MySQL source remains independently executable and unchanged.

## 2. Supported JDBC/Hibernate/DB product-family compatibility is credible — app compatibility not proven
**E-CP12-04 — Spring Boot published BOM:** [Boot4.1.2 managed coordinates](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html) list `com.mysql:mysql-connector-j:9.7.0` and `org.hibernate.orm:hibernate-core:7.4.13.Final`, plus actual Jersey4 and `hibernate-validator:9.1.5.Final` (the **Jakarta-only native validator**, not original Javax). [Hibernate ORM7.4 dialects](https://docs.hibernate.org/orm/current/dialect/) list `MySQLDialect` with **minimum MySQL 8.0**; this is a minimum dialect statement, **not** a version-specific endorsement of every MySQL 9.7/26.10 SQL feature, DDL option or operator behavior.
**E-CP12-05 — vendor Connector/J newer than Boot BOM:** [MySQL current Connector/J manual](https://dev.mysql.com/doc/connector-j/en/) identifies **26.10** as the newest recommended connector for MySQL Server8.0+, [official compatibility matrix](https://www.mysql.com/support/supportedplatforms/compatibility.html) supports recent Connectors with server8.4 and9.7; [Connector/J9.7 details](https://docs.oracle.com/cd/E17952_01/connector-j-en/connector-j-versions.html) say JRE8+, JDBC4.2, server8.0+. Therefore **Boot4.1.2's BOM pins 9.7.0 while vendor latest is 26.10**, both with documented server-family compatibility. A newer driver override is **not automatically necessary or approved**; choose effective version after real build/security/run testing and reproducibility. No Spring-Jersey-JPA-MySQL app was compiled or connected by this research chat.
**Material course constraint:** The modern Boot BOM's Hibernate Validator9 uses `jakarta.validation`; it cannot by itself satisfy the course's **literal** `javax.validation` on source DTO **and** JPA entity callbacks. Provider coexistence and original 26-route semantics remain blocked per [35](35_VALIDATOR_PROVIDER_SECURITY_AND_SUPPORTED_RUNTIME_GATES.md), [37](37_COURSE_SLIDES_TWILIO_VIRTUAL_AND_ENTITY_VALIDATION_AUDIT.md).

## 3. Network boundary for a private managed database
**E-CP12-06 — OCI networking:** [Oracle HeatWave networking](https://docs.oracle.com/en-us/iaas/mysql-database/doc/overview-networking.html) and [connection overview](https://docs.oracle.com/en-us/iaas/mysql-database/doc/overview-connecting-db-system.html) say managed DB endpoints are **not directly public**. With Path B, OCI A1 Java service must reach the private MySQL endpoint through an authorized VCN/subnet/NSG with TCP3306 only from the application VM; never expose 3306 to the public internet. The private network property **does not substitute for** JDBC/TLS transport verification, DB user least privilege, username/key rotation, or auth/tenant checks in Jersey.
**Proposed acceptance:** verify source VM/private DB connectivity, explicitly check TLS connection negotiation/validation and server policy, fail-closed on wrong CA/host and no public 3306 reachable, log only sanitised connection errors. No NSG/VCN/security certificate/DB session configured or observed during CP12. Self-managed Path A DB loopback-only removes VCN service-to-service setup but shares single-VM failure domain.

## 4. Backups and rollback are NOT solved by one-day provider backups
**E-CP12-07 — precise managed Free restore options:** [Oracle backup overview](https://docs.oracle.com/en-us/iaas/mysql-database/doc/overview-backups.html) and [restore guide](https://docs.oracle.com/en-us/iaas/mysql-database/doc/restoring-backup.html) allow automatic Always Free backups with **fixed 1 day retention**, no user manual backup or point-in-time recovery. **FINAL backup on deletion**, *if enabled*, can have up to **7 days retention** for Always Free; not the same as an ongoing seven-day recovery window and must not be claimed a guaranteed final backup. Restore of an Always Free backup to a new Always Free DB system is supported **within the same tenancy** subject to capacity/one-free-system entitlement and restore constraints. This protects a narrow DB failure case, **not** OCI account suspension/tenancy loss, and it does not prove that a replacement free slot is available on demand.
**E-CP12-08 — export portability:** [Oracle HeatWave→MySQL instance](https://docs.oracle.com/en-us/iaas/mysql-database/doc/migrating-mysql-heatwave-db-system-mysql-instance.html) supports MySQL Shell `util.dumpInstance` to local files or cloud object stores; it describes `ocimds: true` to omit service-specific data/privileges, and MySQL Shell version **at least server version**, latest preferred. [Export/import overview](https://docs.oracle.com/en-us/iaas/mysql-database/doc/overview-exporting-and-importing.html) describes compat transformations/checks and warns cross-major version dump loading not fully supported. The portability strategy must cover **application schemas, migration version, Spring JDBC session tables, recovery/credential hashes, authorizations, org/ledger integrity and user-created routines/events**, rather than assuming provider backup can move to another provider. Require client-side encryption, separate key, manifest and SHA256.
**E-CP12-09 — downgrade nuances:** [MySQL9.7 downgrading guide](https://dev.mysql.com/doc/refman/9.7/en/downgrading.html) shows **previous-LTS downgrade via logical dump/load or replication** is permitted **only for rollback** and if no new functionality has been used; it does **not** promise an in-place cross-LTS downgrade. [MySQL upgrade-before-you-begin](https://dev.mysql.com/doc/refman/9.7/en/upgrade-before-you-begin.html) warns certain backwards moves (including 9.7→9.6 or backwards within 9.7 patch versions) are unsupported and instead require pre-upgrade backup restore. Therefore **MySQL.Free 9.7/possibly innovation→self-managed MySQL8.4** is an **unproven version-sensitive migration**, not an unconditional disaster-recovery path. Require actual logical import into a clean 8.4 and exact schema/role/ledger verification; if new SQL/collation semantics block import, plan an approved migration adapter or restore to a compatible supported free engine, never silently downgrade. Whole-schema data export has privacy/security implications for password hashes and recovery tokens even if seed data fictional.
**E-CP12-10 — independent failure domain:** provider snapshots and object storage in **same OCI tenancy** do not protect from an OCI account lock. The official restore workflow is explicitly same-tenancy. Maintain a separately held encrypted export/key and show restore after simulating loss of OCI access, subject to a no-mandatory-spend destination that still needs user/account verification. No cloud backup, cross-provider export, free billing or clean restoration performed during CP12.

## 6. Architecture recommendation and evidence/classification
**DESIGN RECOMMENDATION (not USER DECISION):** Prefer **Path A**, a self-managed genuine MySQL8.4 LTS on eligible OCI ARM64 VM, *for version stability and deterministic academic MySQL testing*, if a supported actual Javax+Jersey runtime can be established and operator can maintain DB/security/backups. Path B genuine managed `MySQL.Free` remains **GO WITH CONDITIONS as a future provider sub-choice only**, not a production GO, due unpinnable highest version, current default vs actual ambiguity, 1-day snapshots and same-tenancy restore. Both remain contingent on zero-charge entitlement, operational stewardship, paid overage hard boundaries, HTTPS/renewal, independent off-provider restored backups and user approval. No course tech change, no registered accounts, no product code or runtime execution.
**Overall decision:** production/full-build **BLOCKED**; research packet still has material unknowns, especially literal true Javax JPA save validation and exact current Canvas/CLO9/Twilio requirement.
**Remaining estimate:** CP11 said **6–10 focused research passes**. This CP12 addresses MySQL/JPA/driver/fallback/version/restore on paper, leaving **approximately 5–9 focused research passes** if no more material gaps emerge. It is not a deadline estimate or claim of gapless prebuild E2E.
