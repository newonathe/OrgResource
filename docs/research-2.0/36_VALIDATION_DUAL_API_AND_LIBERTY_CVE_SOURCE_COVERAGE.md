## 2. MC-24 — two distinct Validation API artifacts may coexist; providers NOT PROVEN
**VERIFIED OFFICIAL ARTIFACT METADATA:**
- [Sonatype Maven Central](https://central.sonatype.com/artifact/javax.validation/validation-api): `javax.validation:validation-api:2.0.1.Final` exposes old Bean Validation 2.0 / `javax.validation` names.
- [Sonatype Maven Central](https://central.sonatype.com/artifact/jakarta.validation/jakarta.validation-api/3.1.1): `jakarta.validation:jakarta.validation-api:3.1.1` exposes current Jakarta Validation 3.1 / `jakarta.validation` names.
- [Hibernate Validator 6.2 vendor](https://hibernate.org/validator/releases/6.2/) says its Javax provider brings **`jakarta.validation:jakarta.validation-api:2.0.2`**, which confusingly contains *javax* packages. **This transitively conflicts at Maven group/artifact selection** with current `jakarta.validation:jakarta.validation-api:3.1.1` if left unmanaged.

**DESIGN INFERENCE, NOT BUILD:** A current Java17 Spring Boot4/Jersey4/JPA/Hibernate/MySQL runtime might retain Jakarta 3.1 API and **separately** add old-coordinate `javax.validation:validation-api:2.0.1.Final`. The APIs have distinct GAV and Java class names; this resolves **one version-choice conflict**, not actual provider lifecycle, autowiring, old DTO constraint validation, security or support. A Javax provider such as [Apache BVal 2.0.6](https://bval.apache.org/downloads.html) uses a different implementation family from current Hibernate Validator9, which might simplify this *specific* coexistence. But it last published June2022; no current maintenance/security guarantee or transitive graph has been checked. For HV6.2, one must handle its old Jakarta2 API transitive and HV9's same Maven provider coordinate; ordinary Maven cannot select both HV6 and HV9 implementations as independent versions under one GAV.

**Genuine provider proof:** [Hibernate Validator6.2 reference, bootstrapping chapter](https://docs.jboss.org/hibernate/validator/6.2/reference/en-US/html_single/) documents `javax.validation.Validation.byProvider(...)` when multiple compatible providers exist. The Javax and Jakarta Validation APIs also use **different ServiceLoader interfaces**. Prove the exact actual provider class, explicitly invoked factory, factory shutdown, nested/groups/container constraints, old DTO invalid→400 response, consistent JSON/error handling. **Spring Framework7 and Jersey4's standard validation remains Jakarta-only; no automatic Javax DTO validation follows from installing two jars.** There is no actual Maven dependency tree, startup, JDK17 validation, request-response, or security test in this research pass.

## 3. MC-25 — newly discovered 2026 Liberty feature-level security restriction
**VERIFIED EXTERNAL SECURITY FACT:** [IBM Nov3 2026 Liberty bulletin](https://www.ibm.com/support/pages/node/7295371) identifies CVE-2026-93879 (EL-related resource exhaustion, CVSS 7.5) in **IBM WebSphere Liberty 17.0.0.3 through 26.0.0.11** with `beanValidation-2.0`/`beanValidation-3.0`/`validation-3.1`. IBM prescribes interim **APAR DT505010** or **26.0.0.12+**. [APAR page](https://www.ibm.com/support/pages/node/7295206) says 26.0.0.12 fix targeted; [recommended updates](https://www.ibm.com/support/pages/node/715553) still show Nov3's 26.0.0.11, so **26.0.0.12 generally available status NOT VERIFIED** on Nov15. Fix distribution may require IBM entitlement; [Open Liberty security catalogue](https://www.openliberty.io/docs/latest/security-vulnerabilities.html) and binary terms must be checked **separately** from IBM WebSphere. An official old Jakarta EE8/Javax feature is not magically a safe deployed Javax/Jersey/Boot4 app. [IBM additional REST bulletin](https://www.ibm.com/support/pages/node/7295357) also flags some older REST features. Liberty's built-in JAX-RS implementation **is not automatically Jersey**.
**Interpretation limit:** The IBM advisory alone does not establish identical patch availability/support entitlement for the **Open Liberty** distribution. No current runtime version, feature or patch was deployed or tested here. No paid fallback approved.
