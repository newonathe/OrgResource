## Finding MC-20: V2 time-window reservation formula is overconservative, not correctly time-weighted
The current [11](11_WORKFLOWS_STATES_AND_INVARIANTS.md) describes `headroom(W) = T - I - SUM(APPROVED.q WHERE overlaps(APPROVED.W,W))`. This **sums mutually non-overlapping reservations** whenever each individually intersects W, even if they never demand the stock at the same instant.

Counterexample with T=5, I=0:
- A q4 [09:00,11:00), B q4 [11:00,13:00): disjoint, both approved and mathematically feasible.
- C q1 [10:00,12:00): feasible for both halves, since A+C=5 from 10–11 and B+C=5 from 11–12.
- **Faulty draft aggregate:** SUM(A+B)=8, headroom=5−8=−3, rejects C.
- **Correct time-window *peak***: `peakH(W) = max over t in W of SUM(q of APPROVED allocations with start<=t<end)`, excluding terminal/expired holds as defined. At each t in C, peakH=4; `headroom= T - I - peakH = 1`, so C q1 may be approved. A q2 [10:00,12:00) would be rejected.
- Use half-open `[start,end)` and a deterministic **event sweep** over clipped start/end boundaries. At a shared timestamp, subtract ending reservations **before** adding starting ones; test 09/11 adjacency, nested/zero-length/boundary, many nonoverlapping overlaps and near-overflow. This is a **design specification**, not tested code.
- Outstanding physical issued `I` is conservatively assumed unavailable for **every future time** until a usable return is recorded; that blocks some feasible distant reservations but does not falsely promise returns. A previously approved future reservation can become `AT_RISK` if older equipment remains issued past the expected return. At actual ISSUE, require on-hand `T - I >= q` after same resource lock; never force release overdue custody to satisfy a future promise. Approved-held q moves to I on issue and must not be counted twice.
- Existing V2 formula is **safe but unnecessarily rejecting** some windows; this finding is about correctness/usefulness, not established overbooking exploitation. New event sweep complexity, additional indexes and failure modes are reasons **not** to include time-window booking in the smallest academic-compatible P0 without user approval.

## Finding MC-21: foreign keys need source-resource integrity, not only same-tenant integrity
Provisional [10](10_EERD_AND_DATA_DICTIONARY.md) enforces `(org_id,parent_id)` but **ledger `stock_movement.resource_id` and `stock_movement.allocation_id` could each reference valid rows in the same org while referring to *different* resources**. Same-tenant alone does not prevent posting a CONSUME against Resource B for an Allocation raised from Resource A.

**Proposed relational keys**, future MySQL V2 only:
| Table | Required keys and cross-reference | Reason |
|---|---|---|
| `department` **new** | `id PK, org_id NOT NULL, public_id, name, name_key`; `UNIQUE(org_id,id)`, `UNIQUE(org_id,name_key)`; FK org | Restore genuine original Department as internal team, **not** as synonym for Organization |
| `project` | `org_id,department_id NOT NULL`; FK `(org_id,department_id) -> department(org_id,id)`; optional LEAD membership separately | Prevent cross-tenant team/project and preserve `departmentId` |
| `resource` | `id PK,org_id NOT NULL`; `UNIQUE(org_id,id)` and `UNIQUE(org_id,name_key)`; kind REUSABLE/CONSUMABLE | One separately owned stock pool per tenant, no shared B rows |
| `requirement` | `org_id,project_id,resource_id NOT NULL`; FK pairs org+project, org+resource; `UNIQUE(org_id,project_id,resource_id)`; `UNIQUE(org_id,id,resource_id)` | Each project/resource unique, exposes invariant for allocation |
| `allocation` | `org_id,requirement_id,resource_id NOT NULL`; composite FK `(org_id,requirement_id,resource_id)->requirement(org_id,id,resource_id)`; `UNIQUE(org_id,id,resource_id)` | Intentional duplicate `resource_id` lets DB verify inherited resource from requirement; requires service consistency |
| `stock_movement` | `org_id,resource_id NOT NULL`; FK to resource org+id; optional `allocation_id` with FK `(org_id,allocation_id,resource_id)->allocation(org_id,id,resource_id)`; `UNIQUE(org_id,operation_public_id)` with durable client operation ID | A movement cannot identify another resource's allocation; ISSUE/RETURN/CONSUME must CHECK allocation_id **IS NOT NULL**; INITIAL/RECEIPT can have NULL |
| `membership` / `audit` | bound org-membership refs; no unrelated global user privilege | Identity records retained but not falsely promoted by resource paths |

**External support:** [MySQL 8.4 foreign keys](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) permit multicolumn constraints; a composite with a NULL key part can escape lookup, so every **mandatory** child org and parent ID must be NOT NULL. [MySQL 8.4 CHECK](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html) only supports same-row expressions, not cross-table stock total and owner count; never mistake CHECK for reservation capacity control. A nullable optional allocation FK intentionally bypasses for certain stock events, **so kind-specific CHECK and service transaction logic must close that gap**. All named DDL, JPQL mappings, index plan, actual MySQL 8.4/ARM support and failed FK insertion tests are future proof obligations. Proposed composite link replication may be too complex for a small academic deadline; do not disguise that tradeoff.

## Finding MC-22: durable unique business operation needed beyond expiring HTTP receipts
The earlier design describes a 24-hour idempotency receipt plus a durable `operation_public_id` uniquely stored in movement history. If the server generates a **new** operation ID upon every HTTP retry after the receipt expires, `RECEIPT +q` and `ADJUST` can still duplicate. A lifecycle status protects duplicate terminal CONSUME/RETURN, but not legitimate repeatable stock receipt.
- Each independently authorized **physical operation** must use an opaque **client-established 128+ bit business operation ID reused on every retry**, carried in request or dedicated header and unique in the immutable operation/movement table within tenant; persist stable request/body fingerprint on the durable record as needed.
- `Idempotency-Key` still determines short-lived HTTP response cache (provisional 24h). Durable business ID is distinct from transient cache retention. Same ID + different payload = conflict; same ID + same payload = confirmed prior outcome, never second ledger event, **even after 48h, restart, or HTTP receipt purge**. Use read-back by durable operation ID after unknown network outcome; no blind retry with new ID.
- After client loses *both* operation ID and response, backend cannot magically distinguish an independent valid stock receipt from a duplicated human action. Operator reconciliation is required; do not claim mathematical exactly-once physical delivery over unreliable networks.
- Prefer distinguish "one API POST attempt" from "one underlying physical act"; all immutable movement ID/custody history and returned/consumed state transitions must reconcile. Use actual MySQL `UNIQUE(org_id,operation_public_id)` and transaction rollback; bad duplicate swallowed as success is unacceptable.

## Finding MC-23: root lock sequencing must reconcile identity and inventory
CP5 [32](32_IDENTITY_STATE_MACHINE_MYSQL_SCHEMA_AND_SECURITY_TESTS.md) proposed organization→membership→account for ownership; earlier V2 [11] proposes resource→requirement→allocation for stock. Organization closure/disable/rules can race resource approval unless every org status transition and resource mutator consistently revalidate tenant state under common lock.
- **Proposed canonical root-first sequence (not proven)**: `organization(org_id)` row lock FIRST for tenant-global status-changing writes and resource mutators requiring closure/role check, then `resource` lock (ascending IDs if >1), then requirement, allocation, ledger/receipt; identity transactions use org root → membership → user; global account disable across orgs locks org IDs ascending before member/account (CP5 ID-16). Reads may use optimistic current membership check but every dangerous write must revalidate inside this transaction. Never call external SMS/identity provider while holding lock.
- Drawback: **organization root lock per stock operation can serialize all unrelated resources within one org**. For small fictional demo may be acceptable; benchmark before making throughput promise. Alternative versioned org state + locking only where necessary must prove close/approve, membership revoke/issue and multi-resource concurrency; not approved as implementation simplification.
- [MySQL InnoDB locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) locks require active transaction; [isolation](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) READ COMMITTED fresh statements vs default REPEATABLE READ snapshot; no stale pre-lock quantity decision. [deadlock guidance](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html) and [error behavior](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html) require rollback and **whole transaction** reattempt after deadlock; lock-timeout may roll back only a statement, so explicitly abort/rollback the outer app transaction. Choose bound retries with stable business operation ID, distinguish repeatable from nonrepeatable effects, never indicate success before commit.

## P0 course-compatible global capacity and ledger contract (proposed V2, NOT executable)
Given a tenant resource `T=total usable/remaining quantity`, global `H=sum APPROVED quantity of still-effective holds`, `I=sum ISSUED outstanding reusable units`:
- Reusable `available = T - H - I`, with `T>=H+I>=0`; consumable `available=T-H`, `T>=H>=0`. **When expiry affects H** the rule must be explicitly decided: O14 JPQL excludes APPROVED once `project.endAt<=now`, while proposal wording says reserve until cancelled/returned/consumed; keep O14 behavior intact pending academic review. Do not both exclude by time and continue counting in another layer.
- Approving PENDING q: lock org/resource/requirement/allocation, verify `q<=available` and requirement uncovered, transition to APPROVED without changing T or I.
- ISSUING approved reusable q: old hold H decreases q; I increases q, T unchanged. Available unchanged immediately; physical on-hand `T-I` becomes lower q. RETURNING **entire usable batch**: I decreases q, T unchanged, available increases q, historical requirement fulfilled coverage retained. No partial/damaged/loss implicit success.
- CONSUMING approved consumable q: T decreases q, H decreases q; available stays the same immediately, history coverage retained. CANCEL PENDING/APPROVED only: release hold, no custody/stock delta. Terminal repeated action denied or read-back per business key; never subtract/add twice.
- This is a tenantized **logical translation of proposal**; original academic JPA classes, scheduled SMS course demonstration, routes and statuses remain unchanged. No actual V2 DB or Jersey code and no capability to claim full production A-ACCEPT.
