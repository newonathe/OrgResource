## B. 2026 security finding — credible impact, carefully scoped
**VERIFIED EXTERNAL SECURITY FACT:** [IBM vendor security bulletin first published 2026-10-21](https://www.ibm.com/support/pages/security-bulletin-hibernate-validator-affected-expression-language-injection-vulnerability-cve-2026-93879) reports **CVE-2026-93879**: user-controlled Expression Language messages may lead to resource exhaustion/denial of service, CVSS3.1 **7.5** per IBM. Vendor lists Hibernate Validator **5.4.1.Final through 6.2.5.Final** and several newer series as affected. **6.2.6.Final** is the corrected Javax-series release. Newer fixed Jakarta series versions are separately listed by vendor. The official October bulletin is a **security advisory**, not evidence that the O14 endpoints permit the necessary exploit conditions.
**VERIFIED HISTORICAL ISSUE:** [NVD/CISA CVE-2025-35036](https://nvd.nist.gov/vuln/detail/CVE-2025-35036) concerns unsafe EL interpolation in HV versions **before 6.2.0**; the later 6.2 releases changed this default. The two CVEs are distinct: one fixed by the initial 6.2 series behavior, a different October 2026 finding fixed by **6.2.6**. Do not collapse or double-count them as a single vulnerability.
**SOURCE-BASED RISK:** If O14 resolves the inherited `6.0.13.Final` as expected, that dependency falls within both cited affected version ranges. This is a **KNOWN DEPENDENCY RANGE RISK**, not a proven remotely exploitable bug, a real attack, or an independently run dependency scan. User-input-to-EL interpolation path and actual transitive libraries must be audited separately. Do not expose legacy Boot2.1 course JAR on the public internet; do not unilaterally upgrade its exact tested academic baseline in this research chat.

## C. Correct packages and documented provider support
| Implementation | API/namespace and vendor support evidence | Decision for an unchanged course + secure public app |
|---|---|---|
| **Hibernate Validator 6.0.13.Final** | Boot2.1.0 manages it; legacy `javax.validation`; older than fixes and original HV6.0 series end-of-life [HV release index](https://hibernate.org/validator/releases/) | Course source inherited version expected and **security range flagged**; no production exposure |
| **Hibernate Validator 6.2.6.Final** | Vendor lists **limited support** with Java **8/11/17**, Jakarta Bean Validation **2.0 using `javax` packages**, officially listed Boot **2.4–2.7** in [HV6.2 compatibility](https://hibernate.org/validator/releases/6.2/); fixes CVE-2026-93879 | True literal `javax` candidate on Java17, **NOT supported Boot4 integration merely by importing**; maintenance/security/EL message rules require review |
| **Apache BVal 2.0.6** | [Apache downloads](https://bval.apache.org/downloads.html) identifies real `javax.validation.spi.ValidationProvider` for Java8 Bean Validation2.0, published **2022-06-13**; its newer 3.x line uses **jakarta.validation** | Separate Javax provider implementation package, possible investigation for coexistence with native Jakarta provider, but 2022 artifact maintenance/advisories/classloader/EL behavior unverified |
| **Native current Spring Framework7/Jersey4** | [Spring Bean Validation](https://docs.spring.io/spring-framework/reference/core/validation/beanvalidation.html) injects `jakarta.validation.Validator`, [Jersey4 user guide](https://eclipse-ee4j.github.io/jersey.github.io/documentation/latest4x/user-guide.html) `jersey-bean-validation` also Jakarta | Required Jersey and Spring technologies available; **not equivalent** to active course `javax.validation` without explicit valid Javax path |
| **Open Liberty EE8** | [Open Liberty Bean Validation2](https://openliberty.io/docs/latest/reference/feature/beanValidation-2.0.html) offers actual `javax` packages on Java21, but [Liberty Boot4 feature](https://www.openliberty.io/docs/26.0.0.10/reference/feature/springBoot-4.0.html) says no automatic integration with Liberty security/REST; Boot4 requires Jakarta EE11 Servlet6.1 | A server providing `javax` does not prove Jersey+Boot4 can invoke it; **UNPROVEN** |
| **Jakarta Bean Validation2 API artifact** | [2019 EE8 Bean Validation 2.0 specification](https://jakarta.ee/specifications/bean-validation/2.0/bean-validation_2.0.html) explicitly uses default package `javax.validation` even when artifact coordinates are `jakarta.validation:jakarta.validation-api:2.0.2` | **Avoid coordinate/namespace confusion:** artifact group `jakarta.validation` does not automatically imply package is `jakarta.validation` in major version **2.x**. Versions **3.x** switch namespace. Proof uses actual class package and version, not name alone |

**Key lifecycle conclusion:** HV6.2.6 is a concrete fixed **javax** implementation. It is **not** on the vendor's supported Spring Boot4 compatibility list; it is in limited-support and the October fix shows that even legacy series can receive fixes when needed, not that future critical fixes are guaranteed. BVal2 having a different implementation family might reduce duplicate `org.hibernate.validator` collisions, but its own upkeep and transitive dependency risks remain UNKNOWN. A single Maven dependency graph with both HV6.2 and HV9 cannot simply pick two versions of the *same coordinate*. No class-loader coexistence or vendor security confirmation has been independently executed.
