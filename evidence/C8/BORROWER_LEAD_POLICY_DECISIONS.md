# C8 borrower and assigned LEAD policy

Status **OWNER APPROVED NOVEMBER 19, 2026**. This policy specifies decisions DEC-02, DEC-03 and the affected DEC-04 operations. Implementation and verification proceed in dependency-ordered batches. Course Final A, the 28 academic compatibility operations, and selected-workspace Reporting retain their existing contracts.

## Identity and assignment

- One optional active LEAD membership per Project. The current organization OWNER or ADMIN can assign, replace or clear it through a versioned Project operation. The target must be an active LEAD in that same organization. A LEAD may edit approved Project fields under the rules below. Assignment changes require OWNER or ADMIN.
- The previous LEAD loses access when reassigned or cleared. Demotion, suspension or revocation clears assignments in the governance transaction. Re-enabling the membership requires a fresh explicit assignment. Assignment continues for historical reads until removed. Existing Project time rules still apply to mutations.
- Link a new reusable request to a current active same-organization borrower membership. A consumable borrower is optional. With no consumable borrower the server uses the requester's display label and leaves the link empty. The server snapshots the authorized display label at creation. A later rename changes the directory label and leaves past snapshots intact. The requesting actor membership is recorded separately.
- Legacy Allocations keep their text snapshots and empty borrower linkage. Never resolve legacy labels by string match. A bound borrower is fixed at creation, including for a pending request. To correct a pending request, an authorized actor cancels it and creates a new one. An inactive linked borrower loses self-service access immediately. Changing access preserves approved or issued custody, stock movements and history. Physical returns and other privileged operations remain available under the existing rules.
- Persist organization-consistent membership relationships with composite foreign keys. Use opaque public IDs on the proposed organization-path contracts. Check active roles, assignment, borrower eligibility and the operation's scope inside the transaction using the existing lock order. Serialize participating governance/assignment changes with writes that depend on them. Keep referenced membership records available for auditable history. Validate current authorization again for replay and receipt reads.

## Permissions by operation

| Actor | Proposed permission |
|---|---|
| OWNER or ADMIN | Set and clear Project LEAD. Keep existing organization-scoped role grants. Discover eligible borrowers for an authorized Project. |
| CUSTODIAN | Keep existing stock and Allocation lifecycle grants. Discover eligible borrowers within an authorized Project. |
| Assigned LEAD | Read the assigned Project, its Requirements and its Allocation records. Edit permitted Project fields, delete an unreferenced assigned Project, and manage its Requirements subject to existing business guards. Create a pending Allocation in that Project. Cancel their own pending requests and delete their own never-approved requests, subject to existing deletion rules. Resolve borrower options through the authorized Project only. |
| Unassigned LEAD | Existing baseline workspace grants. Additional Project and Allocation privileges require a current assignment. |
| MEMBER | Keep existing workspace grants. Read Allocations bound to their own active membership with a minimal self view. Revoke their own bound Allocation's SMS consent, including for a previously ended Project. |
| Bound borrower in another active role | The same minimal borrower self-service scope. Any broader access must come from an independent role grant. |

LEAD creation of a Project stays with OWNER and ADMIN. LEAD cancellation in the proposed policy is limited to PENDING, so cancelling a committed hold remains an existing privileged action. Assignment grants no stock movement, contact access, role administration, organization-wide Allocation list, or export privilege. An assignment never makes the actor the borrower. A borrower has no approve, issue, return, consume, delete, or third-party visibility grant by virtue of a borrower link. The borrower representation contains only their Allocation reference, Project and Resource labels, own quantity, status, and relevant lifecycle dates. It omits other borrowers, contact values, provider data, or audit actors.

## API and failures

- Place the additive routes under `/api/v2/orgs/{orgId}`. Follow the active path membership convention for these routes. `POST /projects/{projectId}/lead-assignment` accepts `{operationId,leadMembershipId}` with a UUID operationId and explicit null to clear. Require the current Project ETag and Idempotency-Key. The operation identifier follows the existing modern mutation receipt convention. Project update cannot write the assignment field.
- Add `GET /borrowers?projectId=…&limit=…&cursor=…&search=…`. Require an authorized Project for every lookup. An assigned LEAD may use the currently assigned Project only. Eligible options contain `membershipId` and `displayName` only. There is no Project-participant model in this proposal. Options are active organization memberships eligible for borrowing under that Project, scoped to its authorized lookup. If Project-specific eligibility is required, approve that relationship before implementation. Cap the page at the existing v2 workspace maximum and bind its cursor to organization, Project and search.
- Define the organization-path Project and Requirement read and mutation grants as above. Scope every LEAD list in SQL by the actual Project association. For Allocations, add the linked borrower field to the modern create operation and use the redacted scoped officer view for assigned Project rows. Provide a separate bounded self view at `GET /borrowed-allocations` and `GET /borrowed-allocations/{allocationId}`, plus a consent revocation action on that self path. Use existing consent-clearing behavior and side effects. Reject a client-supplied borrower name snapshot.
- Apply the existing modern error envelope. Anonymous requests return 401. Conceal inaccessible organizations and out-of-scope rows behind 404. An active member lacking the action grant receives 403 where the route may disclose that resource. Invalid field shape returns 400. An existing same-org borrower or candidate LEAD with ineligible state returns a controlled 409 after authorization. Versioned writes use 428 for missing and 412 for stale ETags. Reject a foreign membership as 404. Redact roster and sensitive values from errors, receipts, logs and exports.

## Evidence required for acceptance

Exercise actual HTTP and MySQL for officer assignment and clear, demotion/reactivation, transfer during a concurrent mutation, and stale ETag or replay after revocation. Cover two tenants, two Projects and two distinct same-name borrowers. Prove authorized LEAD read/edit/request succeeds in one Project and fails in the other, including pagination and cursor reuse. Prove self reads and consent revocation, denial of every other borrower's record, and unchanged actor/history/custody after suspension or a denied write. Cover directory field minimization, absence of contact/provider values, legacy compatibility, retention across restart, preserved stock invariants, and packaged React journeys for both roles.
